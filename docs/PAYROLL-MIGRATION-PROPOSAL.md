# Proposed contractor payroll migration (unexecuted)

Do not apply to a live database yet. Adapt migration 001's workspace/company naming to one canonical scope, verify managed identity and membership, and write PostgreSQL integration tests first. Current preview has no database connection.

1. Extend contractor identity with status, payment method (non-sensitive enum), effective start/end and update timestamps. Keep company + contractor number unique. Existing names/references remain intact.
2. Add append-only contractor_compensation_rules with company/contractor composite foreign key, method enum, integer basis points, flat/per-mile bigint cents, effective dates, active state and creator/time. Require method-specific values and safe integer bounds. Use exclusion constraints on company/contractor effective date ranges for active rules, including simultaneous-write tests. Retain historical versions referenced by settlement lines.
3. Add deduction_rules with company/contractor, category, description, method, frequency, cents/basis-points, explicit percentage base, balance, effective dates and creator/time. Enforce nonnegative safe integer bounds, valid dates, required method fields and installment payment > 0. Track balance changes in an append-only ledger; mutable balance projections need compare-and-set checks.
4. Add company-scoped pay_periods, payroll_runs and payroll_transactions. Transactions require contractor, period, type, reference, date, description, integer cents, whole miles, source and enteredBy/time. Allow signed ADJUSTMENT only; other financial inputs are nonnegative. Runs use DRAFT, REVIEW, APPROVED, PAID, LOCKED, CANCELLED, REVERSED. State transitions require explicit permission and audit; financial content cannot change after approval. A reversal record supplements the original.
5. Add loads with one contractor, company, unique identity, normalized load number, PRO, dates, route, miles, gross integer revenue and status. Detect likely duplicates in staged imports before creation. Use a source-consumption table with unique (company, source kind, source ID) to prevent concurrent reuse in approved payroll. A reference match under a new ID also requires review.
6. Add settlements with unique (company, run, contractor), compensation method/rate, all cents totals, calculation schema version, complete JSON snapshot, approvedBy/time and optional original reversal target. Add settlement_lines with kind, category, signed cents, human explanation, source, rule version, origin and occurrence key. Foreign keys include company to prevent cross-company references. Approved snapshot/lines are append-only; database triggers must reject UPDATE, DELETE and TRUNCATE, including privileged accidental writes. Use separate append-only run state events for payment/lock transitions.
7. Add deduction_applications with unique (company, contractor, rule version, occurrence key), run/settlement line and balance ledger entry. Add unique reversal target per company/contractor/original run. Approval locks all affected sources, rule versions, balances and run records; recalculation, snapshots, occurrence use, balance ledger/projection and audit insert happen atomically. Roll back the entire transaction on any conflict. Reversals need explicit reviewed balance corrections, not automatic source reuse.
8. Expand audit actions beyond contractor.created using explicit allowed events; log actor, company, entity identifiers, timestamp, reason and safe metadata only. Keep append-only enforcement. Never embed bank/tax identifiers in snapshot or audit JSON.
9. Apply FORCE ROW LEVEL SECURITY to every new table with verified organization membership and non-owner/NOBYPASSRLS runtime roles. A browser-selectable workspace context is insufficient. Restrict approvals to a server transaction boundary; no direct client writes to approved tables.

Required integration evidence before enabling production: tenant isolation and missing-context denial, pooled connection isolation, concurrent source/rule/occurrence conflicts, balance compare-and-set rollback, audit atomicity, immutable approvals, duplicate reversal rejection, effective-date overlap exclusion, migration upgrade/restore, and YTD reconciliation including cross-year adjustments. Back up and test restore before migration; rollback application code independently and never drop populated financial tables as a shortcut.
