# Automatic Gmail invoice and receipt tracking

PayCore connects an authorized Gmail/Google Workspace mailbox once, scans its existing Inbox, then checks Gmail history for new messages and Inbox additions. Billing documents are extracted and recorded in PayCore's private `incoming_documents` table automatically, without manual uploads or routine approval. Incoming records are separate from customer invoices, payroll deductions, payroll approval and payments.

The previous sample-only upload workflow and fictional Scan queue are removed. `/scan` is now the real Gmail connection/status screen. `/scan/activity` and the existing Activity Register show automatically recorded incoming documents. `/scan/inbox` and Exceptions show unreadable, ambiguous or duplicate-looking documents. These views use authenticated server APIs, never a local browser-profile name as authorization. Nothing is represented as connected until the services below are configured.

## One-time deployment setup

No live mailbox, Auth0 tenant, database or credentials were available in this development environment. The implementation is tested with a mocked Gmail service and the actual PostgreSQL engine via PGlite; live provider consent and production delivery of scheduled invocations remain unverified. Configure the following outside source control, using `.env.example` as a variable-name template:

1. Auth0 Regular Web Application: `AUTH0_DOMAIN`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`, a random `AUTH0_SECRET` following the SDK's 32-byte hex requirement, and HTTPS `APP_BASE_URL`. Configure the allowed callback as `<APP_BASE_URL>/auth/callback`, logout URL as `<APP_BASE_URL>`, and web origin as `<APP_BASE_URL>`. The official Auth0 Next.js SDK verifies encrypted secure sessions; account names/email in localStorage are never accepted as identity.
2. PostgreSQL 15+ private database: apply migrations `001_contractors.sql` and `002_gmail_documents.sql` with a migration identity. Set `DATABASE_URL` for a separate non-owner, non-superuser, non-BYPASSRLS runtime role. Use certificate-verified TLS to the database and provider encryption/backups at rest. Do not use `rejectUnauthorized:false`.
3. Provision a real company and its Auth0 `sub` membership administratively. Do not add a public self-enrollment endpoint or trust roles/company IDs from a browser profile. Memberships are in `document_company_memberships` with server-managed roles. `OWNER_ADMIN` and `FINANCE` can connect/disconnect; `PAYROLL_SPECIALIST`, `PAYROLL_MANAGER` and `AUDITOR` can read; contractor and approver-only roles cannot read these documents.
4. Google Cloud Web OAuth client: enable Gmail API, configure `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, and register `<APP_BASE_URL>/api/gmail/callback` as the exact redirect URI. Configure the consent screen for the intended organization/users. The only requested Google scope is `https://www.googleapis.com/auth/gmail.readonly`. Google production verification/security requirements for restricted Gmail scopes must be completed before public rollout; testing-mode refresh-token expiry is not a production connection.
5. Set a separate cryptographically random `GMAIL_ENCRYPTION_KEY` (32 bytes / 64 hex characters) and strong `CRON_SECRET` in the deployment secret manager. Do not reuse the Auth0 secret. Mailbox refresh/access tokens, OAuth PKCE verifiers and original-source payloads use AES-256-GCM with company/mailbox/document-specific authenticated context. Back up the encryption key securely: losing it makes stored tokens/originals unreadable. Key rotation requires a controlled decrypt/re-encrypt migration; do not replace the key casually.
6. Enable the included GitHub Actions scheduler (`.github/workflows/gmail-sync.yml`) for best-effort five-minute checks, or configure an authenticated external scheduler / suitable Vercel plan. Set repository variable `PAYCORE_GMAIL_SCHEDULER_ENABLED=true`, repository variable `PAYCORE_APP_URL` to the HTTPS deployment origin, and repository secret `PAYCORE_GMAIL_CRON_SECRET` to the same deployment `CRON_SECRET`. Scheduled GitHub jobs can be delayed and consume runner minutes according to the repository plan. A once-daily Vercel catch-up is included so this change also deploys on plans that restrict cron frequency; it is a daily fallback, not five-minute polling. For frequent tracking the external scheduler must actually be enabled. The runtime must support the configured 300-second worker duration. The endpoint requires `Authorization: Bearer <CRON_SECRET>` and fails closed when dependencies are missing. Never expose that secret to browser code.
7. Sign in securely from Scan, select an authorized company, and authorize Gmail once. Confirm a known invoice is automatically recorded, original-source links open the correct Gmail account, exceptions are visible, and the next scheduled run imports a newly received invoice without a button click. Do not announce the service as live before this check.

The app reports missing setup clearly instead of displaying fictional documents or silently saving private data on the device. All private responses use `Cache-Control: no-store`. Company access resolves the Auth0 session, checks a live database membership, and issues a request-scoped access capability. User IDs/roles supplied in headers or localStorage have no authority.

### Runtime grants

After creating a dedicated runtime role, grant only the following (replace the role name). Do not grant DDL, membership writes, source-record updates/deletes, audit updates/deletes or TRUNCATE:

```sql
GRANT USAGE ON SCHEMA public TO paycore_runtime;
GRANT SELECT ON document_company_memberships TO paycore_runtime;
GRANT SELECT, INSERT, UPDATE ON gmail_mailboxes TO paycore_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON gmail_sync_jobs TO paycore_runtime;
GRANT SELECT, INSERT, DELETE ON gmail_oauth_states TO paycore_runtime;
GRANT SELECT, INSERT ON gmail_processed_messages, incoming_documents, gmail_document_events TO paycore_runtime;
GRANT USAGE, SELECT ON SEQUENCE gmail_document_events_id_seq TO paycore_runtime;
```

Provision memberships using the migration/admin identity in a transaction with `paycore.workspace_id` and `paycore.user_id` set locally to the target company and actual Auth0 subject. Insert into `workspaces` if needed, then `document_company_memberships(company_id,user_id,company_name,roles)`. All private tables force row-level security using transaction-local company scope; membership lookup is scoped to the verified subject. The internal `gmail_sync_jobs` table deliberately supports global service scheduling and contains only company/mailbox IDs and scheduling/lease metadata, never tokens or email contents. It has no browser read endpoint. The scheduler enters a company-scoped transaction before touching private rows.

## Synchronization and failure handling

OAuth uses offline permission, PKCE, a randomized authenticated-encrypted state and a database state entry bound to the signed-in user/company with a ten-minute expiry. Callback state is consumed once. Browser POSTs require the configured same origin. Tokens are never returned to browser APIs. Reconnection resets the backlog checkpoint; content uniqueness prevents repeating previous records.

The initial scan captures a Gmail history anchor before paging the whole current Inbox. Completion switches to incremental history, including `messageAdded` and Inbox-label additions. Messages outside Inbox are not marked as permanently processed; if they later enter Inbox they remain eligible. Expired history restarts a duplicate-safe backlog scan. Invalid pagination cursors restart their current phase. Multiple attachments are processed individually. If an attachment records successfully, incidental email-body text is not recorded again; the body is considered when no attachment could be recorded. Both plain text and HTML mail bodies are supported; scripts/styles/HTML markup are never executed.

The worker leases mailbox jobs with `FOR UPDATE SKIP LOCKED`, checks current lease/active connection before each private transaction, and releases or lets leases expire safely on crashes. A time budget leaves uncompleted message/page checkpoints for the next run. Deferred mailboxes keep their due time so a long-running mailbox cannot starve them. Temporary Google/network errors retain checkpoints and retry automatically. Invalid/revoked refresh grants show a reconnect message. Disconnect erases stored credentials and removes the job; existing documents remain for authorized company readers. Users may separately revoke the app in Google account permissions.

Messages and file bytes are deduplicated with database uniqueness. SHA-256 is unique per company across connected mailboxes. A normalized vendor/reference advisory lock serializes semantic duplicate checks; distinct files with the same vendor/reference go to Exceptions, not a second automatic record. Source inserts and append-only audit events commit together. Exact duplicate files do not create extra entries. Raw messages do not become payroll activity.

## Extraction and limits

Readable PDFs, plain text, HTML and single-record CSVs are parsed into vendor, document/receipt number, date, USD total, address and phone when identifiable. CSV cells map directly to fields, preserving multiline addresses and reference spaces. Dates accept ISO or US month/day/year; totals use exact integer-cent validation. Multiple inconsistent totals, missing required values, unsupported currency or unsupported files become Exceptions, with the original email linked. Extraction is conservative and does not invent missing dates or totals.

Image receipts and PDFs with no selectable text use bundled English Tesseract OCR on the server. The OCR model/core/worker are local dependencies; document contents are not sent to an external OCR or AI service. Native PDF rendering uses the pinned Canvas dependency. Low-confidence OCR goes to Exceptions. Limits are 10 MB per attachment, 30 native-text PDF pages, five scanned PDF pages, 16 million image pixels, and 100,000 extracted text characters. OCR recognition has a per-image timeout; the whole scanned PDF has a time budget. Larger/unreadable documents retain a source-email link and an exception, rather than blocking the mailbox forever. Oversized attachments are not downloaded/archived by PayCore; open their original in Gmail. If a full message exceeds the bounded API-response limit, the worker reads its small metadata response, stores an exception/source link for Inbox messages, and continues instead of retrying that message forever.

Normal source bytes are encrypted in the private database. Structured fields are private database rows, protected by server authorization, RLS, TLS and database encryption at rest. No original files or live business records belong in repository fixtures. English OCR and supported layouts are an initial implementation, not a guarantee of perfect extraction from every invoice format. Source links select the connected Gmail account. List APIs are paginated; the UI refreshes status/records every 30 seconds and clears prior records when access expires or is denied.

## Validation and rollback

Tests cover an actual PostgreSQL engine (PGlite) with the migration, RLS under a separate runtime role, automatic insertion, backlog pagination, incremental replays, revoked leases, retry/checkpoint preservation, encrypted token refresh, semantic/exact duplicates, one-time PKCE/state, token/user binding, real native PDF extraction and local image OCR. Gmail calls are mocked; no private mailbox has been accessed. Auth0, Google consent and the production scheduler need the deployment checks above. Physical Safari and large production mailbox throughput remain unverified.

Rollback: disable the Gmail cron first, then revert the feature commits. Retain private database rows and encryption key for recovery/audit. Do not drop original-source tables or remove company membership data during a UI rollback. The migration adds new tables and does not modify payroll/invoice balances or issued invoices. No production migration or deployment-secret changes have been performed by this task.

The build validates server trace manifests against files nested below directory symlinks, which Vercel rejects during output deployment. OCR/PDF asset includes resolve real package directories before tracing; pnpm's normal package symlinks remain intact. The regression check rejects the former conflicting manifest and passes the corrected manifests while retaining the model, core WASM and PDF worker.
