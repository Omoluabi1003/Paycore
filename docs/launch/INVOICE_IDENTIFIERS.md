# Automatic invoice numbers and stable join keys

Invoice entry proposes INV-YYYY-NNNNNN automatically in a read-only field. The sequence is assigned from the latest saved company book on first successful draft save; viewing/cancelling an unsaved draft consumes nothing. YYYY uses the UTC first-save date, not a later edited service/invoice date. The numeric sequence continues across years within the book. Saved drafts and voids are retained and reserve their numbers. Allocation normalizes existing formatted references, checks safe ranges and cannot create a duplicate. Save retries with the same invoice ID retain the existing number, even if a stale proposed number was sent. The automatic path ignores a caller-supplied display number; the low-level legacy save guard rejects renumbering. Invalid saves consume nothing.

The readable invoice number is a business reference. Future links should use the existing internal invoice.id together with companyId. New UI invoices already generate crypto.randomUUID() once; that ID remains fixed through draft edits, approval/finalization, payments, reversals and voiding. Existing invoice numbers/IDs are preserved, including legacy references. The draft-save domain guard now rejects attempts to renumber an existing record. The low-level manual save path remains for legacy compatibility; the UI uses the automatic allocator exclusively and offers no manual number field.

Invoice summary CSV is now one header and one row per filtered finalized invoice, with Company ID, Invoice ID, Invoice number, company/customer, dates, status, currency and exact total/received/balance cents. A Record mode column labels rows FICTIONAL EXHIBIT. There are no metadata or total rows mixed into this machine-joinable invoice CSV. PDF summaries still contain their totals, and payroll CSV is unchanged. Spreadsheet formula protection remains applied. This is a deliberate invoice CSV format change; existing consumers must select the new named columns rather than rely on old positions.

Exhibition limitations: numbering is scoped to the current profile/company browser-tab book, not an organization-wide production service. Different tabs/profiles/devices or a confirmed demo reset do not share a durable company sequence. Voiding within a retained book never reuses a number; resetting the entire exhibit clears that book intentionally. UUIDs remain the correct future join key. No database or production concurrency guarantee is fabricated.

Production allocation must occur on the authenticated server, in the same transaction as invoice creation, using a company-scoped durable sequence and a unique constraint on company plus invoice number. An idempotency key based on invoice ID must prevent retries from consuming another number. Related records should reference company plus immutable invoice ID, with tenant authorization verified on every operation. No production integration, database migration, sequence provisioning or payment behavior is introduced here.

Validation: regression coverage exercises preview/cancel behavior, automatic allocation, stable IDs, read-only number enforcement, immutable draft references, sequential allocations from stale proposed values, draft/void reservation, company separation, save/restore, year rollover, legacy references, normalized existing numbers, unsafe sequence rejection and joinable CSV exact cents/company boundaries. Existing financial and statement tests remain unchanged.

Rollback: revert this increment to restore manually entered numbers and the prior invoice summary CSV format. Already saved numbers/IDs remain ordinary compatible invoice fields. No schema, storage-version, migration, environment or dependency changes. Do not renumber historical records during rollback.
